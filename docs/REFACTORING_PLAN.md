# VamSerLike 리팩토링 설계 및 실행 계획

- 작성일: 2026-09-20
- 검토 기준: main / `d32cb51aa0c959da173a8692239869bbae1a17d7`
- 환경: Unity 6000.0.37f1, URP 17.0.3
- 상태: 코드 정적 검토와 설계 논의를 정리한 구현 제안. 이 문서의 커밋은 런타임 구현 변경을 포함하지 않는다.
- 검증 범위: 핵심 게임·몬스터·무기·풀·웨이브·저장 코드 및 프로젝트 설정. Unity 실행, 전체 씬 참조 검증, 실제 빌드와 프로파일링은 아직 수행하지 않았다.
- 목표: 게임플레이 기반을 재작성할 수 있는 범위로 재설계하되, 기존 콘텐츠와 기획자의 웨이브 제작 흐름을 보존한다.

## 1. 목표와 범위

### 1.1 목표

1. 시작, 플레이, 성장, 일시정지, 사망, 클리어, 재시작의 상태와 수명을 명확히 한다.
2. 몬스터의 스폰·행동·사망·풀 반환 계약을 통일한다.
3. 모든 몬스터의 행동 실행을 경량 FSM으로 통일하되, 단순한 몬스터에는 단일 상태를 허용한다.
4. 기획자가 코드 수정 없이 몬스터 종류, 배치 모양, 생성 일정과 완료 조건을 조합하도록 한다.
5. 저장 데이터와 게임 콘텐츠의 정의, 한 판의 실행 상태를 분리한다.
6. 기존 플레이 감각을 비교할 수 있는 실행 기준과 회귀 검증을 확보한다.

### 1.2 유지·교체 기준

| 처리 | 대상 |
| --- | --- |
| 유지 | Unity·URP, 원본 그래픽·사운드·애니메이션, 맵 배치와 공포 연출 의도 |
| 검증 후 이식 | 밸런스 수치, 무기·몬스터 프리팹, 보스 패턴, 웨이브 데이터 |
| 재작성 | 자동 생성 싱글톤 의존, 세션 상태, 시간·일시정지, 스탯·상태 효과, 풀 수명주기, 저장 모델 |
| 통합 | 반복되는 무기 코드, 스테이지 정보, UI 데이터 접근, 개발용 도구 |
| 측정 후 결정 | 공간 분할, Jobs/Burst, Addressables, 고급 에디터 도구 |

엔진 업그레이드, DOTS/ECS 전환, 전면적인 아트 교체는 초기 리팩토링에 포함하지 않는다. 프리팹과 씬까지 무조건 새로 만들지 않는다. 새 구조가 스테이지 1을 완주할 수 있을 때까지 기존 실행 경로를 비교 기준으로 유지한다.

## 3. 목표 아키텍처와 의존성

### 3.1 수명별 소유권

| 구성 | 소유 대상 | 수명 |
| --- | --- | --- |
| AppRoot | 설정, 콘텐츠 카탈로그, 저장소, 씬 전환, 공용 오디오 | 앱 |
| RunSession | 현재 스테이지 ID, 경험치, 장비, 버프, 게임 시간, 실행 상태 | 한 판 |
| StageContext | 플레이어, 활성 적 레지스트리, 풀, 웨이브 실행기, 지역 연출 | 스테이지 |
| UI Presenter | 표시 상태와 사용자 입력 연결, 구독 | 화면 |

AppRoot가 명시적인 순서로 의존성을 구성한다. Instance 접근을 통한 GameObject 생성과 전역 이름 검색을 새 코드의 기본 연결 방식으로 사용하지 않는다. 필요한 참조는 초기화 인자나 Inspector 참조로 전달한다.

씬 종료는 스폰 중단 → 행동 종료 → 활성 객체 회수 → 풀 정리 → 이벤트 해제 → 씬 언로드 순서를 가진다. 비동기 완료 콜백은 세션 ID 또는 취소 토큰을 확인하여 이전 세션을 변경하지 못하게 한다.

### 3.2 코드 경계

- Core: 스탯, 경험치, 업그레이드 추첨, 시간·웨이브 규칙 등 테스트 가능한 C# 로직.
- Runtime: Unity 물리, 오브젝트, 애니메이션, 풀 및 씬 연결.
- Presentation: UI와 시청각 표현.
- Editor: 콘텐츠 검증, 가져오기, 미리보기.
- Tests: EditMode와 PlayMode 테스트.

폴더 분리 후 asmdef 의존성을 명시한다. Core가 UI나 Editor에 의존하지 않도록 한다. 모든 클래스를 인터페이스로 감싸거나 별도 DI 프레임워크를 도입하는 것을 목표로 삼지 않는다.

### 3.3 상태와 시간

세션 상태는 Preparing, Running, UpgradeSelection, Paused, Cleared, Failed, Exiting 등을 명시적으로 관리한다. 허용된 전환만 실행하며 사망·클리어 경합의 우선순위를 정의한다.

일시정지 요청은 메뉴·성장 선택·외부 중단 등 사유별로 획득·해제한다. 한 화면이 닫혀도 다른 중단 사유가 남으면 전투는 재개되지 않는다.

전투·버프·스폰 일정에는 세션 시계를 사용한다. 로딩·메뉴·전환 연출에는 비스케일 시간을 사용한다. 초 단위를 기본으로 하고 물리 tick이 필요한 곳만 명시적으로 변환한다.

## 4. 몬스터 구조와 FSM 통일

### 4.1 구성

| 구성 | 책임 |
| --- | --- |
| MonsterActor | 초기화·스폰·사망·반환 조율 |
| Health | 체력, 피해 적용, 사망 1회 보장 |
| MonsterBrain | 행동 FSM, 타깃 판단, 이동·공격 결정 |
| MonsterMotor | 실제 위치 갱신, 속도 보정, 넉백 |
| MonsterPresentation | 애니메이션·사운드·피격·죽음 표현 |
| MonsterDefinition | 기본 수치, 프리팹, 보상 등 공유 설정 |

일반/보스 상속에 FSM 사용 여부를 묶지 않는다. 보스의 역할은 전용 UI, 보상, 완료 조건과 연결하고 행동은 Brain에서 구현한다. 모든 역할을 반드시 별도 MonoBehaviour로 만들 필요는 없다. 작은 순수 C# 객체나 직렬화된 설정으로 충분한 부분은 단순하게 유지한다.

### 4.2 FSM 범위

모든 몬스터는 같은 경량 실행 계약을 사용한다.

| 종류 | 예시 상태 |
| --- | --- |
| 단순 추적 | Chase |
| 체스 폰 | Wait, Jump |
| 원거리 적 | Move, Attack, Recover |
| 퀸 | Idle, Chase |
| 벽장 보스 | Hide, Appear, Attack |

기존 MonsterFSM의 Enter/Update/Exit 개념은 유지할 수 있다. 시작, 정지, 초기 상태 재설정, 잘못된 전환 방어를 보강한다. 상태 Enter 중 또 다른 전환이 요청되는 경우 즉시 재귀 전환 대신 예약 전환 등 일관된 정책을 사용한다. 정지 시 현재 상태 Exit가 한 번만 실행되어야 한다.

- 공유 상태는 실제 공통 동작이 있을 때 추출한다.
- 보스별 전용 상태는 유지한다.
- 한 몬스터 인스턴스가 가진 변경 가능한 상태 객체를 다른 몬스터와 공유하지 않는다.
- ScriptableObject에는 정의만 두고 타이머·현재 타깃 등 실행 상태를 저장하지 않는다.
- 매 프레임 상태 객체를 생성하지 않는다.
- 경직처럼 행동을 중단하는 효과의 우선순위와 재개 정책은 명시한다.

행동 FSM에는 추적·준비·공격·숨기를 넣는다. 독·둔화·무적은 별도 효과 시스템, 피격 섬광은 연출, 사망·반환은 수명주기에서 처리한다. 행동과 상태 효과의 조합마다 새 상태를 만들지 않는다.

### 4.3 이동과 연출

FSM은 이동 의도를 결정하고 이동 전략은 직선·지그재그·점프의 계산을 담당한다. Motor가 실제 이동을 적용한다. 이동 계산에는 타깃과 deltaTime을 전달하고 GameManager 직접 접근을 줄인다.

기존 Transform 이동과 물리 이동의 선택은 충돌 동작을 확인하고 결정한다. 모든 움직임을 일괄적으로 Rigidbody2D로 바꾸지 않는다. 점프가 실제 충돌 위치를 움직이는지 시각적 높이만 표현하는지도 이식 시 기록한다.

이동 코드의 SendMessage 기반 사운드는 타입이 명확한 연출 호출이나 이벤트로 대체한다.

### 4.4 스폰·반환 계약

1. Initialize: 최초 컴포넌트 참조와 실행 객체 준비.
2. OnSpawn(context): 스폰 ID, 위치, 타깃, 체력, 속도, FSM, 타이머, 충돌 상태 설정.
3. Running: 준비가 끝난 뒤에만 행동·충돌을 허용.
4. Die: 살아 있는 상태에서 한 번만 진입. 공격·피해·클리어 알림의 중복을 막음.
5. OnDespawn: 상태 종료, 트윈·코루틴·사운드·이벤트 정리 후 반환.

OnEnable이 초기화 이전에 행동하지 않게 활성화 순서를 설계한다. 죽음 애니메이션이 없는 적과 있는 적 모두 동일한 사망 경로를 사용하고 반환 시점만 다르게 한다. 애니메이션 이벤트가 누락되어도 영구 잔류하지 않도록 종료 보완 정책을 둔다.

## 5. 풀과 개체 추적

공통 풀 기반 위에서 몬스터·투사체·드롭별 초기화 정책을 적용한다.

- 문자열 전역 변수에 의존하는 생성 콜백을 없애고 풀별 프리팹·부모 참조를 고정한다.
- 초기 생성 수, 유휴 보관 상한, 동시 활성 상한을 구분한다.
- 활성 객체와 유휴 객체 모두 추적하고 스테이지 종료 때 정리한다.
- 같은 객체의 중복 반환을 막는다.
- SpawnHandle은 객체 식별자와 재사용 세대를 포함한다.
- 이전 세대의 타이머, 애니메이션 콜백, 패턴 정리 요청은 무시한다.
- 제거 이유를 Killed, PatternExpired, StageUnloaded 등으로 구분한다.

GameObject가 비활성이라는 사실만으로 처치나 웨이브 완료를 판정하지 않는다. 보스 패턴의 강제 만료가 보스 처치로 인정되는지는 명시적 기획 정책으로 결정한다.

## 6. 웨이브와 배치 제작 구조

### 6.1 유지할 설계

기획 데이터, 배치 좌표 계산, 일정 실행, 실제 생성의 분리는 유지한다. SpawnFormation은 에디터 미리보기와 런타임에서 공유 가능한 계산기로 발전시킨다. 초기부터 노드 편집기를 만들지 않는다.

### 6.2 제안 데이터 모델

| 정의 | 주요 필드 |
| --- | --- |
| StageDefinition | 안정적인 ID, 표시 정보, 씬 경로, 웨이브, 드롭, 완료·보상 |
| WaveDefinition | ID, 시작 조건, 패턴 목록, 완료 조건 |
| SpawnInstruction | 몬스터 참조, 생성 일정, 배치 설정, 기준 위치, 남은 적 처리 |
| FormationDefinition | 종류, 개체 수, 크기, 회전, 오프셋, 흩뜨림 |
| SpawnSchedule | 한 번/반복/순차 생성, 간격, 횟수 또는 생성 기간 |
| SpawnAnchor | 플레이어/고정 위치/지정 지점, 기준점 갱신 정책 |

기존 StageSpawnPattern과 WavePatternData는 이 모델로 변환하거나 이름과 필드를 점진적으로 정리한다. 재사용할 필요가 없는 모든 항목을 독립 에셋으로 만드는 것은 피한다.

### 6.3 모양과 생성 방식 분리

Random을 지속 생성의 특수 분기로 두지 않는다.

- 모양: 원둘레, 직선, 다각형 테두리, 무작위 영역 등.
- 방식: 한 번에 생성, 일정 간격 반복, 한 마리씩 생성.
- 수량: 회당 개체 수와 전체 생성 한도 구분.
- 기준 위치: 반복마다 플레이어를 다시 기준으로 삼을지, 패턴 시작 위치를 고정할지 명시.
- 동시 제한: 제한에 도달하면 대기·생략·종료 중 하나를 선택.

예: “이전 웨이브 종료 5초 후 플레이어 주변 반지름 8에 폰 12마리를 원형 생성, 4초 간격으로 3회 반복.”

몬스터 종류의 기본 데이터에 있는 spawnRate는 패턴별 일정으로 이전한다. 같은 몬스터를 두 패턴이 동시에 생성해도 서로의 코루틴을 중단하지 않도록 실행 인스턴스별 ID로 관리한다.

### 6.4 시간·종료 조건

| 개념 | 예시 |
| --- | --- |
| 시작 조건 | 스테이지 시작 30초 후 / 이전 웨이브 종료 5초 후 |
| 생성 종료 | 3회 생성 / 10초 동안 생성 |
| 웨이브 완료 | 소유한 적 전멸 / 지정 보스 처치 / 시간 경과 |
| 남은 적 처리 | 유지 / 회수 |
| 중첩 허용 | 앞 웨이브와 병행 / 앞 웨이브 완료 대기 |

상대 시간의 기준을 Inspector에 표시한다. 현재의 waveStartTime은 스테이지 기준이지만 패턴 시간은 웨이브 시작 기준인 점을 이전 시 보존·표시한다. 프레임 지연으로 여러 예약 시간이 지나간 경우 따라잡기 실행 정책과 프레임당 생성 한도를 정의한다.

전멸 조건은 아직 생성할 몬스터가 남아 있지 않고 소유한 활성 스폰이 0일 때 만족한다. 랜덤 생성도 소유권 추적에 포함한다. 빈 패턴·생성 실패·보스 누락을 자동 성공으로 처리하지 않도록 검증한다.

### 6.5 좌표 계산 보완

- 삼각형·사각형 나머지 수를 분배하거나 둘레 길이 기준 균등 샘플링으로 정확히 N개 생성.
- N=0, N=1, 변 수보다 작은 N에 대한 명시적 결과.
- 원은 반지름, 선은 전체 길이, 사각형은 가로·세로로 표시.
- 꼭짓점 포함 여부, 테두리/내부 채우기 구분.
- 흩뜨림 방향과 범위 명시.
- 고정 난수 시드를 주입하여 같은 입력에 같은 배치를 재현.
- 좌표 생성과 장애물·화면 경계 등 유효 위치 검사를 분리.

유효 위치가 없을 때 무한 재시도하지 않는다. 제한된 재시도 후 생략 또는 다른 지점 사용 정책을 선택한다. 플레이어 안전 거리도 검증 단계에 포함한다. 위치 보정은 모양을 흐트러뜨릴 수 있으므로 미리보기에 보정 결과를 표시한다.

### 6.6 기획자 편집 UX

우선 구현할 기능:

1. 몬스터 에셋 선택과 썸네일, 문자열 이름 입력 제거.
2. 선택한 모양·생성 방식에 필요한 필드만 표시.
3. Scene 뷰에서 실제 계산기를 이용한 생성 위치 미리보기.
4. 개수·간격·기간·미등록 참조·완료 불가능 조건 검증.
5. 패턴 복제, 정렬, 활성/비활성, 단일 패턴 시험 실행.
6. 시간·수량·완료 조건을 사람이 읽는 문장으로 요약.
7. 고정 시드와 미리보기 시간 조절.

JSON 가져오기는 임시 데이터에 파싱·검증한 후 전체 성공 시 적용한다. 실패 전에 기존 목록을 지우지 않는다. jsonFile 미지정, 잘못된 JSON과 잘못된 참조를 안내한다. Undo/Redo, 변경 저장 처리를 지원한다.

ScriptableObject와 JSON 중 어떤 것이 원본인지 명시한다. 기본안은 ScriptableObject를 편집 원본으로 하고 JSON은 가져오기·내보내기용으로 사용한다. 기존 JSON 중심 제작 흐름이 실제로 사용 중이면 이식 전에 확인한다.

## 7. 전투·성장·무기

### 7.1 스탯과 상태 효과

기본값, 고정 증가, 비율 증가, 최종 배율의 계산 순서를 명시한다. 현재 목록 순서에 따른 결과를 기준 샘플로 기록하고 새 공식으로 바꿀 때 밸런스 변경을 별도로 검토한다.

효과에는 ID, 출처, 지속 시간, 중첩·갱신 정책을 둔다. 이름에 손전등·야간투시가 포함되는지로 효과를 결정하지 않는다. 만료 목록 순회 중 삭제를 방지한다. 변경 시 계산을 갱신하고 불필요한 매 프레임 전체 재계산을 줄인다.

### 7.2 성장

대량 경험치를 모두 처리한 뒤 필요한 업그레이드 선택을 큐에 쌓는다. 레벨·필요 경험치 등 상태를 확정한 후 이벤트를 발행한다. UI가 열려 있다는 이유로 추가 선택을 버리지 않는다.

후보는 현재 소유·최대 레벨·슬롯 수를 기준으로 먼저 필터링하고 중복 없이 추첨한다. 후보가 부족하거나 모두 최대 레벨이면 명시적 대체 보상 또는 종료 정책을 적용한다.

### 7.3 무기와 타깃

WeaponDefinition에 수치·아이콘·프리팹·공격 방식을 모은다. Axe/Hammer 등 공통 동작은 합치고 산탄·장판·궤도 등 실제로 다른 동작은 분리한다. Type.GetType 기반 이름 생성은 명시적 참조나 등록된 팩토리로 대체한다.

활성 적 레지스트리를 사용하고 최근접 탐색은 우선 선형 최소값 탐색으로 정렬을 제거한다. 검색 주기·공유 가능성을 검토하고 프로파일링 후 공간 분할 도입 여부를 결정한다.

## 8. 저장·UI·연출

### 8.1 저장

- ProfileSave: 해금, 소유 장비·스킨, 영구 진행.
- RunSave: 한 판의 상태. 현재 이어하기 지원 범위를 조사한 뒤 보존 범위를 확정.
- SettingsSave: 음량·입력 등 사용자 설정.

명시적인 DTO와 schemaVersion, 안정적인 콘텐츠 ID를 사용한다. 임의 CLR 타입명과 현재 씬 객체 존재 여부를 저장 스키마의 기준으로 삼지 않는다.

사용자 쓰기 경로는 persistentDataPath로 통합한다. 기존 SaveManager의 임시 파일·백업·재시도 의도는 유지하되 저장과 복원이 같은 파일을 동시에 변경하지 않게 직렬화한다. 플랫폼별 파일 교체·복구 동작을 검증한다.

이전 절차: 구 파일 백업 → 구 포맷 읽기 → 검증 → 새 DTO 변환 → 새 파일 기록 → 재로드 검증 → 이전 완료 표시. 실패하면 원본을 보존한다. 현재 씬에 없는 ID를 일괄 삭제하지 않는다. 기존 사용자 데이터가 없거나 복호화·파싱에 실패하는 경우도 구분한다.

### 8.2 UI와 입력

UI는 파일·JSON을 직접 읽지 않고 읽기 모델과 명령을 사용한다. 구독·해제를 화면 수명에 맞춘다. 장비 선택과 실제 시작 무기 연결을 확인하고 PlayerAttack의 고정 Shotgun 생성 경로를 대체한다.

기존 마우스 임시 입력과 Input System의 혼용을 조사하고 대상 플랫폼별 이동·조준·일시정지 입력을 명시적으로 연결한다.

### 8.3 공포 연출

보스가 전역 VFX를 직접 초기화하는 대신 연출 요청의 소유자와 수명을 추적한다. 보스 퇴장 시 해당 요청만 해제한다. 중첩 연출의 우선순위·블렌딩·기본값 복원 규칙을 정한다. 강제 디스폰과 씬 전환도 정리 경로를 거친다.

## 9. 단계별 실행과 완료 기준

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 0. 기준 확보 | Unity 빌드 재현, 실행 경로·정상/결함 기록, 참조·저장 샘플·성능 기준 확보 | 변경 전 비교 가능한 빌드와 목록 존재 |
| 1. 기반 | AppRoot, RunSession, 시간·일시정지·씬 전환, 콘텐츠 ID·저장 스키마 | 시작·중단·재시작 반복 안정 |
| 2. 전투 최소본 | 체력·스탯·풀·FSM, 폰·퀸, 근접·투사체 무기 | 단순 적과 보스의 스폰·사망·재사용 계약 검증 |
| 3. 스테이지 1 | 성장 큐, 웨이브 일정·추적·배치, 클리어·보상 | 시작부터 클리어/사망·재시작까지 완주 |
| 4. 콘텐츠 이식 | 나머지 무기·지원 아이템·몬스터·스테이지, 기획 도구 | 이식 목록과 참조·동작 비교 완료 |
| 5. 전환 | 저장 이전 검증, 구 코드 제거, 빌드 구성·CI·문서 | 깨끗한 체크아웃에서 테스트·대상 빌드 성공 |

핵심 의존 순서: 세션·시간 → 수명주기·풀 → 몬스터·전투 → 웨이브·성장 → 전체 콘텐츠. 저장 스키마와 ID는 1단계에서 결정하며 마지막에 덧붙이지 않는다.

기획 도구는 3단계에서 최소 미리보기와 검증을 제공하고, 4단계의 실제 콘텐츠 이식 과정에서 사용성을 보완한다.

## 10. Unity 콘텐츠 이전 규칙

1. 기존 씬·프리팹·SO·애니메이션 이벤트·UnityEvent의 참조 목록을 먼저 작성한다.
2. 파일 이동 시 .meta를 함께 이동하고 GUID를 보존한다.
3. 직렬화 필드 이름 변경은 필요한 경우 FormerlySerializedAs 또는 명시적 변환 도구를 사용한다.
4. 클래스·네임스페이스·컴포넌트 교체는 GUID 유지 여부만으로 안전하다고 가정하지 않는다.
5. 기존 enum 숫자를 재배열하지 않고 안정적인 ID로 변환한다.
6. 변환 도구는 사전 검증, 변경 목록, 재실행 안전성, 실패 시 복구를 제공한다.
7. 공용 프리팹을 즉시 덮어써 기존 실행 경로를 깨지 않도록 새 경로용 변형 또는 복사본을 사용한다.
8. 빌드 대상의 Missing Script, 누락 참조, 애니메이션 이벤트 수신 메서드를 검사한다.
9. 스테이지별 체크리스트가 통과된 뒤 해당 구 실행 경로를 제거한다.

## 11. 검증 계획

### 11.1 EditMode

- 스탯 계산 순서, 효과 중첩·갱신·동시 만료.
- 대량 경험치, 최대 레벨 후보, 업그레이드 큐.
- FSM Enter/Exit 횟수, 중첩 전환 요청, Stop/Reset.
- 배치 개수 0·1·2·3·4·10, 유한 좌표, 회전·크기·고정 시드.
- 웨이브 절대/상대 시간, 중첩, 지연 프레임, 생성 실패와 종료 조건.
- 저장 버전 변환, 잘못된 ID·손상 데이터, 기존 데이터 보존.

### 11.2 PlayMode

- 폰 점프 도중 반환 후 다른 위치에 재스폰.
- 보스 공격 중 강제 반환, 연출·FSM·충돌 초기화.
- 동일 프레임 중복 피해·사망·반환.
- 이전 스폰 콜백과 패턴 만료가 재사용 개체에 영향을 주지 않음.
- 같은 몬스터를 동시에 생성하는 두 패턴의 독립 실행.
- 일시정지 중 씬 전환, 메뉴와 성장 선택의 중첩.
- 연속 재시작·스테이지 전환 후 이전 세션 이벤트 잔류 없음.
- 애니메이션 이벤트 누락 시 반환 보완 경로.

### 11.3 빌드·성능·기획자 검증

실제 대상 플랫폼과 빌드 백엔드를 기준으로 에디터 외 환경을 검증한다. 현재 지원 플랫폼은 ProjectSettings와 기존 배포물을 확인하여 확정한다.

동일 기기·빌드 설정·콘텐츠 부하에서 프레임 시간, GC 할당, 메모리, 활성 개체 수를 비교한다. 목표 FPS와 최대 적·투사체 수는 기준 측정 후 확정한다. 반복 세션에서 메모리·이벤트·코루틴이 계속 누적되지 않아야 한다.

기획자 검증 과제: 코드 수정 없이 원형 반복 생성, 이전 웨이브 후 시작, 보스 처치 완료를 작성하고 미리보기와 실행이 일치하는지 확인한다. 잘못된 참조와 JSON 입력이 기존 데이터를 훼손하지 않아야 한다.

- 기능 커밋은 필요한 .meta와 에셋 연결을 함께 포함하여 중간 상태의 컴파일·참조 오류를 피한다.
- 새로운 구조의 스테이지 1이 완주 가능하기 전 기존 기본 실행 경로 유지.
- 전체 이식·저장 검증 후 main으로 전환.
- 전환 전 기준 커밋/릴리스를 기록하고 문제 시 코드와 데이터의 복구 경로 확보.
- 이 문서는 사용자 요청에 따라 main에 직접 추가하는 문서 커밋이며, 위 브랜치 전략은 후속 구현에 적용한다.

## 13. 구현 중 확정할 정책

아래는 현재 코드만으로 단정하지 않고 기준 확보 단계에서 확인할 항목이다.

- 실제 배포 대상, 목표 FPS, 동시 적·투사체 수.
- 이어하기가 보존해야 할 한 판 상태의 범위.
- 플레이어 사망과 보스 처치가 같은 프레임에 발생했을 때 결과.
- 스폰 실패·유효 위치 부족 시 생략/대기/대체 위치 정책.
- 기존 웨이브의 시간·강제 회수 동작 중 기획 의도와 임시 구현의 구분.
- 새 스탯 공식 적용 시 허용할 밸런스 변화.
- JSON과 ScriptableObject 중 실제 제작 원본 및 협업 방식.

정책이 필요한 부분은 코드 추측으로 바꾸지 않고 동작 샘플과 제안안을 함께 기록한다. 일반적인 구현 선택은 이 문서의 원칙 안에서 진행한다.
